# 对本课题的写作借鉴：先准备论证，再起草正文

这是一份读后建议，不是论文稿、最终贡献列表或新实验指令。本轮不改研究方向，不改算法，不启动实验。

## 1. 先固定这篇论文究竟要回答什么

研究范围以 `ZNS_GC_RR_Research_Plan.docx` 为准。建议把待验证的问题表达为：在顺序写和有限 Open/Active 资源下，什么条件能使协同放置减少 ZC 与 RR 的累计搬运，而不只是转移维护成本或消耗更多空间？

这只是研究问题，尚不是肯定答案。当前[第六阶段第一步方案](../../../../research/rrzc/results/placement-ablation-20261105/阶段六/第一步-准入规则设计/最小实施方案.md)明确区分 Flush 来源与热写/短寿命，提醒准入受限后可能增加普通区压力、Finish 丢尾和后续维护。该方案描述的是其撰写时的候选设计，不能作为当前最终实现已有效的证明。后续写正文前应核验最新代码和归档版本。

## 2. 学习写法时，落实到我们需要准备的材料

|阅读得到的建议|本课题应准备的材料|还不能提前写的结论|
|---|---|---|
|像 FineRR-ZNS 一样，先展示粒度造成的成本|同一维护事件中的有效数据组成、读计数分布、实际陪迁|所有 RR 都浪费相同比例，或所有陪迁都可避免|
|像 μScope 一样，从现象到路径证据|对象身份、申请入口、目标代际、复制和映射记录；必要时延迟观测|单看耗时就断言 SSD 介质慢，或普通回退必然是根因|
|像 ADAPT 一样，明确模块职责与实现边界|RocksDB、ZenFS、FEMU 图；新写入与迁移入口；准入与回退语义|设计提案、示意图中的模块全部已实现|
|像 FAST 样例一样，列出优化的反作用|RR 与 ZC 分项及总量、资源占用、空间压力、应用性能|减少 RR 次数就提高可靠性、寿命和性能|
|像 MSST 样例一样，分离机制贡献|可比配置下的放置、准入、回退或选择器对照|一张总收益图即可归因到每个模块|
|像 JSA 能效研究一样，说明统计阶段|共同业务窗口、必要收尾、末态空间与未完成维护|业务结束前少复制就代表完整周期少复制|

## 3. 将来章节中的段落应该做什么

这是可讨论的组织建议，不改现有 LaTeX 章节。

1. **Background / Problem Definition**：先定义 ZC、项目 RR、H/W/HW、放置单位及资源预算。把源标签、观测热度和未来寿命分开。
2. **Motivation**：用少量可追溯事件说明什么时候有共置机会，什么时候仍有效的数据反复陪迁，以及分配路径为什么会改变预期。每个现象对应一个设计需求，观察不到的未来不补全。
3. **Design**：先给总览，再解释目标选择、准入、必要迁移与普通回退；明确安全条件、资源取得/释放和前进条件。最终机制以冻结版本为准。
4. **Evaluation**：先写要回答的问题，再配图和对照：总搬运是否减少、来自哪条路径、是否付出空间或性能代价、在哪些条件失效。
5. **Related Work / Discussion**：比较决策层、使用的信息、约束和目标；承认共置等已有思想。局限直接对应证据边界，不只写“未来扩大实验”。
6. **Introduction / Abstract / Conclusion**：等论证成立后再确定主张及数字，不先写“显著提升”迫使实验迎合措辞。

## 4. 图的规划也应先绑定问题

|候选图|要让读者看懂的问题|进入正文的前提|
|---|---|---|
|分层系统图|谁观察、谁决定、谁复制、谁提交映射和 Reset|与最终实现逐项核对|
|一条维护时间线或组成图|机会何时出现，又如何因仍有效的 W 而失效|事件和对象身份闭合；示例明确标为示意|
|ZC/RR 分项及总搬运|减少的是总量还是分项转移|单位、窗口和成功/撤销副本口径一致|
|末态空间与资源图|是否靠未偿还空间压力换取表面收益|区分可写尾部、空 zone、可回收空间和占用令牌|
|消融与边界图|哪个机制有效，什么条件下无效|同对请求、起点、配置和账目经过核验|

上述是图的功能清单，未用示例数字生成论文结果图，也不要求每项必须独占一张图。
